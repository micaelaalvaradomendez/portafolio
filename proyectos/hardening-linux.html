1. Contexto & Diagnóstico del Problema

De la Teoría a la Ingeniería de Infraestructura Segura

En entornos empresariales e institucionales, la mayoría de los incidentes de seguridad no provienen de vulnerabilidades de día cero (0-day), sino de configuraciones permisivas por defecto, falta de segmentación de red y ausencia de criterios de bastionado continuo. Este proyecto surgió para consolidar la formación técnica del Diplomado Universitario en Redes Linux, Ciberseguridad y Hacking Ético en un entorno de laboratorio 100% reproducible y auditable.

Superficie Expuesta

Servicios legacy (vsftpd anónimo, SSH con contraseñas débiles) accesibles directamente desde redes públicas sin filtrado perimetral.

Ceguera Operativa

Ausencia de auditoría de eventos de kernel (`auditd`), lo que permite manipulación de identidad (`/etc/shadow`) o sudoers sin rastro forense.

Desafío de Kernel

Docker comparte el kernel del host: parámetros `sysctl`, módulos y `auditd` exigen un diseño híbrido con VM real para no falsear las pruebas.

Decisión Arquitectónica Clave (Laboratorio Híbrido): Se diseñó un entorno dual: Docker Compose sobre redes macvlan para la segmentación perimetral, filtrado nftables, emulación de ataques con Kali/Nmap y fail2ban; y una VM dedicada Debian 13 (Vagrant + libvirt) para el bastionado de bajo nivel del sistema operativo (`sysctl`, inmutabilidad `auditd -e 2`, AppArmor y CIS Benchmark real).

2. Topología de Red & Aislamiento Estricto

Segmentación por Zonas (WAN, DMZ, MGMT) con macvlan

Para asegurar que ningún paquete pueda esquivar al firewall perimetral, el laboratorio descarta los bridges estándar de Docker y utiliza tres redes macvlan `internal` vinculadas a interfaces dedicadas del nodo `fw`. De este modo, el tráfico entre zonas debe ser ruteado e inspeccionado obligatoriamente por el kernel de `fw`.

Al operar en modo `internal`, las redes macvlan no tienen salida a Internet en runtime (todo el software se aprovisiona durante la fase de build). El atacante no tiene visibilidad de la red de gestión y el servidor de la DMZ no puede iniciar conexiones hacia MGMT.

Independencia del Host

El tráfico entre contenedores nunca toca el subsistema `br_netfilter` ni las reglas iptables del host anfitrión (evitando interferencias con Docker, K8s o k3s locales).

3. Filtrado Perimetral & Anti-Escaneo (nftables)

Políticas Fail-Closed, Conjuntos O(1) y Protección Raw

En lugar de reglas dispersas o sintaxis iptables obsoleta, se configuró una tabla unificada `inet hns_filter` en el nodo `fw`. El conjunto de reglas prioriza la evaluación basada en bytecode en kernel y la inspección de estados:

firewall/nftables.conf — Fragmentos Críticos nft 
# Cadena prerouting en prioridad raw: descarta escaneos ilegales ANTES del conntrack
chain scan_filter {
    type filter hook prerouting priority raw; policy accept;

    # NULL scan (-sN), XMAS scan (-sX: FIN|PSH|URG), SYN+FIN y FIN sin ACK
    tcp flags & (fin|syn|rst|psh|ack|urg) == 0 counter log prefix "hns-scan-null: " group 1 drop;
    tcp flags & (fin|syn|rst|psh|ack|urg) == fin|psh|urg counter log prefix "hns-scan-xmas: " group 1 drop;
    tcp flags & (syn|fin) == syn|fin counter log prefix "hns-scan-synfin: " group 1 drop;
}

# Cadena forward: filtrado de paso estricto por zonas
chain forward {
    type filter hook forward priority filter; policy drop;

    ct state established,related accept;
    ct state invalid counter drop;

    # WAN -> DMZ: solo servicios públicos en conjunto dinámico (puerto 80)
    iifname "wan" oifname "dmz" ip daddr @dmz_hosts tcp dport @public_tcp ct state new counter accept;

    # MGMT -> DMZ: SSH solo desde hosts autorizados con rate limit de nuevas conexiones
    iifname "mgmt" oifname "dmz" ip saddr @mgmt_hosts ip daddr @dmz_hosts tcp dport @mgmt_tcp \
        ct state new limit rate over 20/minute burst 20 packets log prefix "hns-ssh-ratelimit: " group 1 counter drop;
    iifname "mgmt" oifname "dmz" ip saddr @mgmt_hosts ip daddr @dmz_hosts tcp dport @mgmt_tcp ct state new counter accept;

    # Respuesta diferenciada: Drop silencioso a WAN vs Reject explícito a redes internas
    iifname "wan" counter drop;
    counter reject with icmpx type admin-prohibited;
}

Diferencial Técnico (Reject vs Drop verificado en pcap): El laboratorio incluye una captura de red automatizada (`make pcap-demo`) que demuestra forensemente cómo WAN recibe descarte pasivo (el escaneo de Nmap se congela esperando retransmisiones y timeout), mientras que un host en MGMT recibe un paquete `ICMP type 3 code 13 (Communication administratively prohibited)` en menos de 1 milisegundo.

5. Defensa Reactiva contra Fuerza Bruta (fail2ban + nftables)

Bloqueo Dinámico en Kernel en Tiempo O(1)

Incluso en la red de gestión (`mgmt`), una estación de trabajo podría sufrir una intrusión. Para contener el movimiento lateral, el servidor de la DMZ ejecuta fail2ban con acción directa sobre nftables (`banaction = nftables-multiport`):

  • Integración con rsyslog: En contenedor sin systemd, sshd escribe eventos nominales a `/var/log/auth.log` y fail2ban procesa los reintentos fallidos en tiempo real.
  • Conjuntos Dinámicos de nftables: Al detectarse 3 fallos en menos de 10 minutos, fail2ban añade la IP atacante a `addr-set-sshd` en la tabla `inet f2b-table`.
  • Demostración Automatizada (`make fail2ban-demo`): Un script reproducible lanza Hydra con contraseñas erróneas desde `admin`, constata el baneo en kernel y comprueba que las conexiones posteriores son rechazadas de inmediato.
  • Restauración Limpia: Concluido el test, la IP es desbaneada y la disponibilidad del laboratorio vuelve al 100%.
