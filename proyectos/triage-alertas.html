Triage Forense de Alertas, Desmontaje de Falsos Positivos & Calibración de Detectores

Análisis cuantitativo de incidentes en plataforma web de soporte: descubrimiento de una campaña multi-vector avanzada subclasificada como fuerza bruta lenta, desmontaje de reportes externos de caja negra (PHP2Shell CVSS 9.2), mitigación de falsos positivos masivos en XSS/SMTP y diseño de detectores pasivos desacoplados en Go y PostgreSQL.

1. Resumen Ejecutivo & Métricas Cuantitativas

La Realidad Operativa: Separar Señal de Ruido

En infraestructuras corporativas con aplicaciones web legacy (LAMP), la falta de parches inmediatos de fabricante exige implementar controles compensatorios basados en detectores pasivos. Sin embargo, un motor de detección teórico sin calibración contextual satura a los analistas de seguridad con falsas alarmas, ocultando incidentes críticos.

Durante la operación sobre una plataforma web de soporte corporativo, el sistema de auditoría registró 21 alertas agregadas de 8 tipos distintos. El triage forense no se limitó a "cerrar tickets": desmanteló falsos positivos masivos, identificó que un grupo de intentos lentos de login correspondía en realidad a una campaña coordinada multi-vector de 13 días y desmontó técnicamente los reportes de herramientas de caja negra frente a la configuración efectiva del servidor.

Surgieron de un proceso formal de ingeniería inversa sobre vulnerabilidades corregidas en versiones superiores de la aplicación: cada parche de seguridad fue modelado como una firma pasiva para detectar si actores externos intentaban explotar dichas fallas en producción.

4. Investigación de Incidente: Campaña Multi-Vector Avanzada

La IP Subclasificada: De "Fuerza Bruta Lenta" a Reconocimiento Activo

Uno de los hallazgos más relevantes del triage surgió al analizar la IP 198.51.100.36. Inicialmente, el sistema la agrupó como una alerta menor de fuerza bruta (15 intentos fallidos distribuidos a lo largo de días, con una tasa casi imperceptible de 0.2 intentos/hora para evadir umbrales volumétricos).

Al cruzar cronológicamente las tablas de eventos del sistema (system_audit_log y ticket_thread_entry), se descubrió que esta IP ejecutó una campaña de reconocimiento y explotación activa de 13 días sondeando sistemáticamente múltiples clases de vulnerabilidades:

Al correlacionar por IP a través de múltiples tablas de auditoría, se reveló una campaña hostil completa con intentos de RFI, File Upload y Path Traversal, justificando el bloqueo perimetral total de la dirección.

5. Threat Intelligence & Análisis de Red (OSINT)

Trazabilidad de Infraestructura Adversaria

Ante los picos de fuerza bruta en el portal administrativo, se aplicaron técnicas de inteligencia de amenazas (Threat Intelligence) y análisis forense de red sobre las IPs atacantes más persistentes para evaluar su infraestructura y capacidades:

MTR, Traceroute & Enrutamiento

Se ejecutó análisis MTR y traceroute bidireccional identificando 21 saltos de red con convergencia a través de enlaces transoceánicos hacia servidores VPS comerciales alojados en centros de datos internacionales (GoDaddy LLC / AS26496).

• Rango: 198.51.100.0/24 (ASN Comercial)
• Latencia promedio: 404 ms (21 saltos)
• Reverse DNS (PTR): host.secureserver.net
Reconocimiento Activo del Atacante

El escaneo Nmap defensivo sobre el host atacante reveló servicios de correo (Exim 4.99) y servidores web con banners activos, confirmando que las peticiones provenían de servidores comprometidos o proxies comerciales utilizados para enmascarar el origen del ataque.

• Open Ports: 22/tcp (SSH), 80/tcp, 443/tcp, 587/tcp
• Táctica: Servidor de relay intermedio
• Acción: Registro en feed de reputación IP institucional
6. Auditoría Crítica: Desmontando la Caja Negra (CVE-2026-109618)

PHP2Shell (CVSS 9.2): La Ilusión de la Sonda Externa

En octubre de 2026, los centros de respuesta a incidentes publicaron la vulnerabilidad crítica PHP2Shell (CVE-2026-109618 / CVE-2026-109619), consistente en el abuso del parámetro reservado PHP_SESSION_UPLOAD_PROGRESS en peticiones multipart para forzar la escritura de código en archivos de sesión y buscar RCE. Una auditoría externa de caja negra reportó vulnerabilidad crítica porque los formularios del servidor devolvían HTTP 200 OK ante solicitudes multipart de prueba.

Aceptar ese reporte hubiera provocado el bloqueo de funciones esenciales (la creación de tickets legítimos con archivos adjuntos en /tickets/crear requiere multipart). Mediante un análisis de causa raíz se demostró que el reporte era un falso positivo por limitación de visibilidad externa: para que exista RCE se requiere una cadena de 3 eslabones obligatorios, neutralizada formalmente en el runtime:

1. Inyección Neutralizada de Raíz

La directiva session.upload_progress.enabled = 0 fue comprobada en caliente con ini_get() en la SAPI web. El intérprete ignora el campo malicioso y no escribe buffers en los archivos de sesión.

2. Sin Vector de Inclusión (LFI)

La aplicación carece de rutas que permitan inclusión local arbitraria, y allow_url_include = Off bloquea wrappers remotos, impidiendo cargar archivos temporales.

3. Confinamiento de Comandos

Mediante disable_functions se restringieron funciones críticas (exec, system, shell_exec, popen). Un control deliberado registró en log el bloqueo efectivo de ejecución.

// pgDetectPHPUploadProgress inspecciona operaciones históricas ingestadas
// buscando cadenas asociadas a sondeos de CVE-2026-109618 sin penalizar tráfico legítimo.
func (s *SecurityScanner) pgDetectPHPUploadProgress(ctx context.Context, windowDays int) ([]AlertFinding, error) {
    query := `
        SELECT id, ip_origen, uri_acceso, payload_raw, created_at
        FROM audit_operations
        WHERE created_at >= NOW() - ($1 || ' days')::INTERVAL
          AND (
              payload_raw ILIKE '%PHP_SESSION_UPLOAD_PROGRESS%'
              OR payload_raw ILIKE '%session.upload_progress%'
              OR uri_acceso ILIKE '%upload_progress%'
          )
        ORDER BY created_at DESC LIMIT 100`

    rows, err := s.db.QueryContext(ctx, query, windowDays)
    if err != nil {
        return nil, fmt.Errorf("falla al consultar audit_operations: %w", err)
    }
    defer rows.Close()

    // El detector clasifica y calcula el score CVSS 9.2 automáticamente
    return s.processUploadProgressFindings(rows)
}

Lecciones de Ingeniería & Madurez Profesional

La experiencia en este caso sintetiza el rol de un analista de ciberseguridad moderno: la seguridad efectiva no consiste en instalar herramientas comerciales y reenviar alertas automáticamente, sino en comprender los fundamentos del sistema operativo, el intérprete y el código para discernir con evidencia empírica qué constituye una amenaza real y qué es mero ruido operativo.
